# 方案文档 Review 循环（多 Agent 并行 + 自动修复 + 量化放行）

## 功能

并行派出多个只读 Review 子 Agent，各自专注一个维度审查方案文档；各 Agent 除报问题、产出结构化修复建议（patch）外，还给本维度打分；主会话维护 Finding 台账、合并建议后串行落盘、写入轮次留痕，并自动启动下一轮复核（只做修复半径内的收敛验证，不做全文重扫），直到总分达标或触发熔断。全程无需逐轮人工确认，用户可随时打断。

## 核心原则

1. **先读代码再 review**：子 Agent 必须主动读取方案文档中引用的项目代码，结合现有代码逻辑和数据结构判断方案可行性。仅凭文档本身做 review 会遗漏关键上下文，问题质量低甚至错误。
2. **多 Agent 分工**：按维度并行（代码对照 / 流程架构 / 风险审计 / 开源对照 / 对抗审计），各维度独立审查、互不阻塞；每轮编队与模板固定，保证审查方向一致。
3. **生成并行、落盘串行**：修复建议的"生成"随 review 并行（各 Agent 附带 patch）；"落盘"只由主会话串行执行——多 Agent 同时写同一文档会互相覆盖。
4. **自动闭环**：patch 合并落盘后立即自动复核，两处均不再询问用户。
5. **量化判据**：各维度 0-10 分按固定权重折算百分制；**放行 = 总分 ≥85 且零 P0**；熔断看分数趋势而非仅问题数。
6. **收敛契约（单调性）**：未决问题集合只能经「修复并验证」或「接受风险」缩小，只能因「改动区域」或「台账外的新代码证据」扩大；复核轮禁止全文重扫——收敛靠台账状态，不靠重复扫描。
7. **熔断保护**：最多 5 轮，到顶自动停止并转人工裁决，防止死循环烧 token。

## 使用方式

用户给出方案文档路径（或明确要审哪份文档）后启动。未提供路径时：优先找 `docs/specs/`、`docs/design/` 等常见方案文档目录，列出候选请用户选择；都没有则直接询问。多份 spec 可同时各起一套编队并行 review（编队之间天然独立）。

## 工作流程

### 1. 确定方案文档

- 用户提供了路径 → 使用该路径
- 未提供 → 搜索常见方案文档目录列候选；无结果则询问

### 2. 并行派出 Review 子 Agent 编队

**在同一条消息内同时发起多个子 Agent 调用（并行执行，不要串行）**。编队如下：

| Agent | 维度 | 审查内容 | 启动条件 |
|-------|------|----------|----------|
| A 代码对照 | 字段映射 + API 兼容性 | 文档定义的字段/结构体/API 参数与返回值，逐一对照代码实际 | 必选 |
| B 流程架构 | 流程完整性 + 异常处理 | 文档描述的流程 vs 代码实际流程；错误处理模式与项目既有风格一致性 | 必选 |
| C 风险审计 | 遗漏风险 | 并发、事务、一致性、性能、容量、安全——代码中实际存在但文档未考虑的风险 | 必选 |
| D 开源对照 | 上游组件 + 资源定义 | 引用的开源组件实现一致性；K8s CRD/资源定义核对 | 仅当文档引用了开源组件或 K8s 资源时派出 |
| E 对抗审计 | 设计假设对抗 | 隐性假设、实现分歧、测试歧义、治理缺失、架构脆弱——挑战设计本身 | 仅当 spec 触及数据面存储（数据库/缓存）、生产写路径、关键扩展链，或用户点名「红队审」时派出 |

子 Agent 派发要点：
- 用通用子 Agent（如 general-purpose），**只读分析，禁止修改任何文件**——prompt 中显式声明
- 完整的子 Agent prompt 模板（首轮骨架、复核轮附加指令、维度专属指令、E 对抗人设段）见 `references/agent-prompts.md`，按模板填充文档路径、项目根目录、维度指令
- 子 Agent 的 prompt 只传：文档路径、项目根目录、（复核轮的）台账 + 已落盘 diff；不传当前会话历史上下文
- 各 Agent 完全独立并行，互不等待

### 3. 汇总、折算与留痕（主会话执行）

全部子 Agent 返回后：
1. **去重**：多 Agent 报同一根因的合并为一条，标注来源 Agent
2. **编号入账**：新问题分配 Finding ID（`R<轮>-<维度字母>-<序号>`，如 R1-C-02），状态 `open` 写入台账；复核结论更新对应 ID 状态（修复成立→`verified`；修复不成立→重开并关联新发现）
3. **统一分级**：P0（阻断）/ P1（必修）/ P2（建议）
4. **合并 patch 建议**：多个 Agent 改同一小节的，综合两边依据重写为一条；拿不准的抽查代码核实
5. **折算总分**：权重池 A30 / B30 / C25 / D15 / E15，只按本轮实际派发（未冻结）的维度按比例归一化到百分制；**冻结判定**——某维度本轮 ≥85 且零 P0/P1 → 标记 frozen（后续轮不重派、分数不变，除非 patch 触碰其段落则解冻）
6. **轮次留痕**：写 `docs/reviews/<spec文件名>.review-status.md`（不与 spec 混放；每轮追加：轮次/日期/派发编队/各维度分/总分/verdict/Finding 台账快照/已落盘 patch 摘要）；通过后标记 APPROVED 收档
7. 向用户展示本轮摘要（**不等待确认，直接进入步骤 4**）

### 4. 自动落盘（主会话串行执行，不询问）

1. 按每条 patch 的「定位」摘录搜索原文，逐条替换落盘；P2 无歧义的顺手落，有歧义的列「遗留建议」
2. 落盘完成后，对应 Finding 状态改为 `fixed（待复核）` 写入台账
3. **设计方向保护阀**：若某 patch 的实质是改变设计方向（而非修正文档与代码事实的偏差），不要擅自定方向——列出决策点请用户裁决后再继续
4. 落盘完成后立即进入步骤 5

### 5. 自动复核（不询问）

按修复波及面与**轮次预算递减**决定重派范围：
- **受影响维度轮（默认）**：只重派被 patch 触碰的维度，注入"复核轮附加指令"（验证修复 + 爆炸半径，禁全文重扫）；frozen 且未被触碰的维度不重派
- **全编队轮**：仅首轮，或修复跨多维度/波及共享小节/波及面不确定时
- **预算递减**：第 2 轮汇总起，仍未修的 P2 全部转入风险登记表（状态 `accepted-risk`，不再修）；第 3 轮起各 Agent 进入 verify-only（只受理 patch 引入的回归）；第 5 轮纯验证（不产生新 finding）

轮数 R+1。受影响维度轮只更新该维度分，总分以最近一次覆盖全部应派（未冻结）维度的轮次为准并标注 partial。

### 6. 终止条件与熔断

| 条件 | 动作 |
|------|------|
| 某轮覆盖全部应派（未冻结）维度，总分 ≥85 且零 P0，台账中无 `open` 状态 Finding；且该轮后如有落盘修复，已完成一次验证轮无新增 P0/P1 | **通过**：status 文件标记 APPROVED，输出最终报告 |
| 轮数 R > 5 | **熔断**：停止循环，输出累计报告 + 未决清单，转用户人工裁决 |
| 连续 2 轮总分不涨（全编队轮间比总分；受影响维度轮比该维度分） | **无进展熔断**：停止并转人工——修 A 坏 B 或措辞无法解决的分歧，可能需要改方案方向本身 |
| 用户主动打断 | 随时生效，输出当前累计状态 |

**熔断后人工裁决三选一**（结果写入 review-status.md，留审计链）：
1. **带风险放行**：未决 Finding 全部转入风险登记表并标注「用户接受」，作为放行凭证
2. **定点人修**：用户拍板决策点后，跑定向验证轮（可只重派受影响维度）再放行
3. **退回重写**：回方案设计阶段重新构思——写码前退回，永远比写码后返工便宜

## 最终报告格式（通过或熔断时输出）

### 🏁 判决
[通过 / 熔断转人工] + 总分表（各维度分、总分、逐轮趋势、冻结状态）

### 📒 Finding 台账快照
| ID | 维度 | 等级 | 状态 | 依据/解决摘要 |

### 📝 已落盘修复摘要

### ⚠️ 风险登记表（遗留 P2 与接受的风险）
| 风险 | 等级 | 依据(文件:行) | 缓解 | 是否阻断 |

## 注意事项

- **台账是收敛契约的载体**：复核 Agent 只信台账与 patch diff，不信「重新全文扫一遍」；无进展熔断若复现「修 A 坏 B」的台账反复开合，即方向问题信号，果断转人工
- 修复落盘只在主会话**串行**执行；并行化在生成侧（核心原则 3）
- 修复只改**方案文档**，不动项目代码；子 Agent 只读不改，patch 建议仅是报告文本
- `*.review-status.md` 统一落 `docs/reviews/`、随仓库提交纳管（审计链）；评分仅供流程判据，不替代人工对风险量级的最终判断
- token 成本：首轮 3~5 个子 Agent（E 按需）；复核轮只看 diff + 台账，显著低于首轮；最多 5 轮
- 每轮子 Agent 都是全新上下文，只传最新文档路径与台账/diff，不带上一轮会话记忆
- **链路衔接**：本技能管"写码前"（spec ↔ 代码库验证）；通过后进入实现阶段（编码实现可另行安排任务拆解与实现评审）
