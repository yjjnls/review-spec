# /review-spec - 方案文档 Review 循环（多 Agent 并行 + 自动修复 + 量化放行）

## 功能
在 superpowers 会话内**并行派出多个 Review 子 Agent**，各自专注一个维度审查方案文档；各 Agent 除报问题、产出结构化修复建议（patch）外，还给**本维度打分**；主会话维护 **Finding 台账**、合并建议后**串行落盘**、**写入轮次留痕**，并**自动启动下一轮 re-review**（只做修复半径内的收敛验证，不做全文重扫），直到总分达标或触发熔断。全程无需逐轮人工确认，用户可随时打断。

## 核心原则
1. **先读代码再 review**：子 Agent 必须**主动读取方案文档中引用的项目代码**，结合现有代码逻辑和数据结构判断方案可行性。仅凭文档本身做 review 会遗漏关键上下文，问题质量低甚至错误。
2. **多 Agent 分工**：review 按维度并行（代码对照 / 流程架构 / 风险审计 / 开源对照 / 对抗审计），各维度独立审查、互不阻塞；每轮编队与模板固定，保证审查方向一致。
3. **生成并行、落盘串行**：修复方案的"生成"随 review 并行（各 Agent 附带 patch 建议）；"落盘"只由主会话串行执行——多 Agent 同时写同一文档会互相覆盖。
4. **自动闭环**：patch 合并落盘后立即自动 re-review，两处均不再询问用户。
5. **量化判据**：各维度 0-10 分按固定权重折算百分制；**放行 = 总分 ≥85 且零 P0**；熔断看分数趋势而非仅问题数。
6. **收敛契约（单调性）**：未决问题集合只能经「修复并验证」或「接受风险」缩小，只能因「改动区域」或「台账外的新代码证据」扩大；复核轮**禁止全文重扫**——收敛靠台账状态，不靠重复扫描。
7. **熔断保护**：最多 5 轮，到顶自动停止并转人工裁决，防止死循环烧 token。

## 使用方式
写完方案文档后（superpowers 用户即在 brainstorming 产出 spec 后），运行：
```
/review-spec <方案文档路径>
```
例如：
```
/review-spec docs/superpowers/specs/2026-05-25-portal-route-management-design.md
```
多份 spec 可同时各起一套编队并行 review（编队之间天然独立）。

## 工作流程

### 1. 确定方案文档
- 用户提供了路径参数 → 使用该路径
- 未提供 → 优先找 `docs/superpowers/specs/`（superpowers 约定），其次 `docs/specs/`；都没有则直接询问用户要审的文档路径

### 2. 并行派出 Review 子 Agent 编队
**在同一条消息内同时发起多个子 Agent 调用（并行执行，不要串行）**。编队如下：

| Agent | 维度 | 审查内容 | 启动条件 |
|-------|------|----------|----------|
| A 代码对照 | 字段映射 + API 兼容性 | 文档定义的字段/结构体/API 参数与返回值，逐一对照代码实际 | 必选 |
| B 流程架构 | 流程完整性 + 异常处理 | 文档描述的流程 vs 代码实际流程；错误处理模式与项目既有风格一致性 | 必选 |
| C 风险审计 | 遗漏风险 | 并发、事务、一致性、性能、容量、安全——代码中实际存在但文档未考虑的风险 | 必选 |
| D 开源对照 | 上游组件 + K8s 资源 | Higress/Envoy 等上游实现一致性；CRD/资源定义核对 | 仅当文档引用了开源组件或 K8s 资源时才派出 |
| E 对抗审计 | 设计假设对抗 | 隐性假设、实现分歧、测试歧义、治理缺失、架构脆弱——**挑战设计本身** | 仅当 spec 触及受保护运行时资源（如 MySQL/Redis 等数据面组件）、生产写路径/DNAT、新 WasmPlugin 链，或用户点名「红队审」时派出 |

每个子 Agent 均为 `general-purpose` 类型，**只读分析，禁止修改任何文件**。

**Task Description**: "Review design spec dimension <X> against project codebase"

**Task Prompt 模板**（首轮全文审查用；复核轮在此骨架上追加"复核轮附加指令"）：
```
你是一名资深系统架构师，负责审查设计文档的【{维度}】维度。只读分析，不要修改任何文件。

## 你要审查的文档
{doc_path}

## 项目根目录
{project_root}

## 你的专属维度（只审这个维度，不要越界到其他 Agent 的职责）
{按下方"维度专属指令"填入}

## 工作流程
1. 使用 Read 完整阅读方案文档，标记与本维度相关的：文档声明、引用的代码路径、API、配置项
2. **必须主动阅读代码验证**（用 Read/Glob/Grep）：文档提到的文件 + 项目中相似的既有实现作参照；若引用开源组件，读项目内 vendor/clone 的上游代码
3. 交叉验证本维度：代码实际 vs 文档声明
4. 按下方格式输出 Review 报告

## Review 报告格式
### 📋 代码上下文确认
[列出你读了哪些文件及路径，以及它们当前的作用]
### ⭐ 本维度总体评价
[一句话：优秀/良好/需要修改/有重大风险]
### 🎯 本维度问题清单
- [P0/P1/P2] [问题类型] [文件:行] - [具体问题：代码中实际是什么、文档中写的是什么]
### 🔧 修复建议（patch 形式，供主会话合并落盘；你不修改任何文件）
- [P0/P1/P2] 定位：<文档中的原文摘录，须与原文逐字一致且足够唯一可搜索>
  改为：<完整替换文本（不是方向描述）>
  依据：<代码文件:行> 一句话说明代码事实
### 📊 本维度评分
X/10 —— [一句话理据；评分必须与问题清单一致：存在未修复 P0 不可能高分]
### ✅ 本维度结论
**是否可进入实施**（仅就本维度）：是 / 否（需先修复列出的问题）
```

**复核轮附加指令**（仅复核轮注入 Task Prompt，替换工作流程段）：
```
## 本轮为第 {R} 轮复核（只做收敛验证，不做发散探索）

## Finding 台账（来自 review-status.md，权威裁决记录）
{open 清单：ID/等级/摘要；verified 与 accepted-risk 清单：ID/裁决依据}

## 本轮已落盘的修改
{patch 摘要：定位段落 → 修改内容}

## 复核规则（硬性）
1. 只验证上述修复是否成立 + 检查修改段落的爆炸半径（相邻小节一致性）；**禁止全文重扫**
2. 新问题只受理两种来源：位于被改动段落内；或附带台账中不存在的新代码证据（文件:行 事实）
3. 翻已裁决案件（verified / accepted-risk）必须附新证据，否则视为重复，不计数、不影响评分
4. 引用已有问题必须带其 Finding ID（如 R1-C-02）
```

**patch 建议的硬性要求**：
- **自包含**：主会话不重读代码即可落盘；依据只作审计线索
- **定位摘录**必须逐字来自文档且在全文唯一（含足够上下文）
- **改为**必须是可直接替换的完整文本；不确定怎么改的，只报问题不硬凑 patch
- P2 问题给 patch 与否随意，P0/P1 尽量给

**维度专属指令**：
- **A 代码对照**：字段映射（文档字段与代码 model/struct 逐一定义对照，含类型、必填性、默认值）；API 兼容性（参数、返回值、错误码与现有实现是否匹配）
- **B 流程架构**：流程完整性（代码实际流程是否支撑文档描述的流程，含分支与边界）；异常处理（现有错误处理模式 vs 文档设计）；新增 model/接口与项目既有风格一致性
- **C 风险审计**：并发、事务、一致性、性能、容量、安全；只报**代码中实际存在**且文档未考虑的风险，逐条标注风险等级与依据文件:行
- **D 开源对照**：上游组件对应版本的实现方式；K8s 资源/CRD 定义核对（字段名、apiVersion、required 项）；方案与上游设计的一致性
- **E 对抗审计**：见上方人设段

**E 对抗审计的专属人设段**（替换进"维度专属指令"位）：
```
你是最严格的 senior engineer + staff architect + QA lead + 治理评审者的合体。你的职责不是让 spec 好看，而是找出会导致返工、实现分歧、治理失败、隐性假设、测试歧义、架构脆弱的每一个问题。必须全量审（通读全文）——局部审是坏 spec 溜过去的口子。目标是防止昂贵错误，不是批评。重点攻击：未被言明的假设、实现者会走岔的设计留白、无法验证的验收表述、与既有运行时的隐性冲突。
```

**对所有子 Agent 的注意事项**：
- 必须用 Read/Glob/Grep 主动探索代码，不得仅凭文档推断
- 不传递当前会话的历史上下文，只传文档路径、项目根目录与（复核轮的）台账+diff
- 各 Agent 完全独立并行，互不等待

### 3. 汇总、折算与留痕（主会话执行）
全部子 Agent 返回后，主会话：
1. **去重**：多 Agent 报同一根因的合并为一条，标注来源 Agent
2. **编号入账**：新问题分配 Finding ID（`R<轮>-<维度字母>-<序号>`，如 R1-C-02），状态 `open` 写入台账；复核结论更新对应 ID 状态（修复成立→`verified`；修复不成立→重开并关联新发现）
3. **统一分级**：P0（阻断）/ P1（必修）/ P2（建议）
4. **合并 patch 建议**：多个 Agent 改同一小节的，综合两边依据重写为一条；拿不准的抽查代码核实
5. **折算总分**：权重池 A30 / B30 / C25 / D15 / E15，只按**本轮实际派发（未冻结）的维度**按比例归一化到 100 分制；**冻结判定**——某维度本轮 ≥85 且零 P0/P1 → 标记 frozen（后续轮不重派、分数不变，除非 patch 触碰其段落则解冻）
6. **轮次留痕**：写 `<spec同目录>/<spec文件名>.review-status.md`（每轮追加：轮次/日期/派发编队/各维度分/总分/verdict/Finding 台账快照/已落盘 patch 摘要）；通过后标记 APPROVED 收档
7. 向用户展示本轮摘要（**不等待确认，直接进入步骤 4**）

### 4. 自动落盘（主会话串行执行，不询问）
1. 按每条 patch 的「定位」摘录搜索原文，逐条替换落盘；P2 无歧义的顺手落，有歧义的列「遗留建议」
2. 落盘完成后，对应 Finding 状态改为 `fixed（待复核）` 写入台账
3. **设计方向保护阀**：若某 patch 的实质是改变设计方向（而非修正文档与代码事实的偏差），不要擅自定方向——列出决策点请用户裁决后再继续
4. 落盘完成后**立即**进入步骤 5

### 5. 自动 re-review（不询问）
按修复波及面与**轮次预算递减**决定重派范围：
- **受影响维度轮（默认）**：只重派被 patch 触碰的维度，注入"复核轮附加指令"（验证修复 + 爆炸半径，禁全文重扫）；frozen 且未被触碰的维度不重派
- **全编队轮**：仅首轮，或修复跨多维度/波及共享小节/波及面不确定时
- **预算递减**：第 2 轮汇总起，仍未修的 P2 全部转入风险登记表（状态 `accepted-risk`，不再修）；第 3 轮起各 Agent 进入 verify-only（只受理 patch 引入的回归）；第 5 轮纯验证（不产生新 finding）
轮数 R+1。受影响维度轮只更新该维度分，总分以最近一次覆盖全部应派（未冻结）维度的轮次为准并标注 partial。

### 6. 终止条件与熔断
| 条件 | 动作 |
|------|------|
| 某轮覆盖全部应派（未冻结）维度，**总分 ≥85 且零 P0**，台账中无 `open` 状态 Finding（全部 `verified` 或 `accepted-risk`）；且该轮后如有落盘修复，已完成一次验证轮（可受影响维度）无新增 P0/P1 | **通过**：status 文件标记 APPROVED，输出最终报告 |
| 轮数 R > 5 | **熔断**：停止循环，输出累计报告 + 未决清单，转用户人工裁决（见下） |
| 连续 2 轮总分不涨（全编队轮间比总分；受影响维度轮比该维度分） | **无进展熔断**：停止并转人工——修 A 坏 B 或措辞无法解决的分歧，可能需要改方案方向本身 |
| 用户主动打断 | 随时生效，输出当前累计状态 |

**熔断后人工裁决三选一**（结果写入 review-status.md，留审计链）：
1. **带风险放行**：未决 Finding 全部转入风险登记表并标注「用户接受」，作为放行凭证
2. **定点人修**：用户拍板决策点后，跑定向验证轮（可只重派受影响维度）再放行
3. **退回重写**：回 brainstorming 重新想方案——写码前退回，永远比写码后返工便宜

## 最终报告格式（通过或熔断时输出）
### 🏁 判决
[通过 / 熔断转人工] + 总分表（各维度分、总分、逐轮趋势、冻结状态）
### 📒 Finding 台账快照
| ID | 维度 | 等级 | 状态 | 依据/解决摘要 |
### 📝 已落盘修复摘要
### ⚠️ 风险登记表（遗留 P2 与接受的风险）
| 风险 | 等级 | 依据(文件:行) | 缓解 | 是否阻断 |

## 注意事项
- **台账是收敛契约的载体**：复核 Agent 只信台账与 patch diff，不信「重新全文扫一遍」；无进展熔断若复现「修 A 坏 B」的台账反复开合，即方向问题信号，果断转人工
- 修复落盘只在主会话**串行**执行；并行化在生成侧（核心原则 3）
- 修复只改**方案文档**，不动项目代码；子 Agent 只读不改，patch 建议仅是报告文本
- `*.review-status.md` 与 spec 同目录、随 spec 提交纳管（审计链）；评分仅供流程判据，不替代人工对风险量级的最终判断
- token 成本：首轮 3~5 个子 Agent（E 按需）；复核轮只看 diff + 台账，显著低于首轮；最多 5 轮
- 每轮子 Agent 都是全新上下文，只传最新文档路径与台账/diff，不带上一轮会话记忆
- **链路衔接**：本命令管"写码前"（spec ↔ 代码库验证）；通过后接 `superpowers:subagent-driven-development` 进"写码中"（每任务 implementer + task-reviewer，同为 fan-out 模式）
